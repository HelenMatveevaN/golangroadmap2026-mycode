# Шпаргалка по конкурентности в Go: когда и что использовать

В Go (Golang) для решения задач конкурентности есть множество инструментов. Эта таблица-шпаргалка поможет вам мгновенно выбрать правильный подход в зависимости от архитектурной ситуации.

## Сводная таблица

| Ситуация | Инструмент | Суть и краткий совет |
| :--- | :--- | :--- |
| **Запустить код параллельно** | `go func()` + `sync.WaitGroup` | Запускаем горутины, а `WaitGroup` гарантирует, что `main` не завершится раньше, чем они отработают. |
| **Передать результат между горутинами** | Канал (`chan`) | Главный способ общения в Go («Не делитесь памятью, общаясь; общайтесь, делясь памятью»). |
| **Несколько горутин, один получатель** | Паттерн **Fan-in** | Сведение (мультиплексирование) нескольких каналов от разных воркеров в один результирующий. |
| **Один источник, несколько получателей** | Паттерн **Fan-out / Worker Pool** | Распределение однотипных задач из одного канала между пулом запущенных горутин-воркеров. |
| **Цепочка преобразований** | Паттерн **Pipeline** | Серия этапов (функций), соединенных каналами, где выход одного этапа является входом для следующего. |
| **Защита общего состояния** | `sync.Mutex` или `sync/atomic` | `Mutex` блокирует доступ к переменной/структуре. Для простых счетчиков (`int32`/`int64`) атомики (`atomic.AddInt64`) работают быстрее. |
| **Инициализация один раз** | `sync.Once` | Гарантирует, что тяжелая инициализация (например, подключение к БД или загрузка конфига) выполнится ровно 1 раз, даже из 100 горутин. |
| **Много читателей, мало писателей** | `sync.RWMutex` | Позволяет множеству горутин читать данные одновременно, но блокирует всех (и читателей, и писателей), когда идет запись. |
| **Ограничить параллелизм** | Семафор через `chan struct{}` | Буферизированный канал емкостью `N`. Перед работой пишем туда пустую структуру, после — читаем. Больше `N` воркеров не запустятся. |
| **Отмена по сигналу** | `context.WithCancel` | Позволяет вручную вызвать `cancel()`, чтобы мгновенно остановить все дочерние горутины, слушающие `ctx.Done()`. |
| **Таймаут операции** | `context.WithTimeout` / `WithDeadline` | Автоматически отменяет контекст (и связанные операции вроде HTTP-запросов), если они длятся дольше указанного времени. |
| **Группа горутин с обработкой ошибок** | Пакет `golang.org/x/sync/errgroup` | Прокачанный `WaitGroup`. Если хоть одна горутина завершилась с ошибкой, `errgroup` прервет остальные и вернет эту ошибку. |
| **Дедупликация одинаковых запросов** | Пакет `golang.org/x/sync/singleflight` | Спасает от «эффекта толпы» (cache stampede). Если 100 пользователей одновременно просят одну тяжелую страницу, выполнится только 1 запрос к БД, а результат раздастся всем 100. |
| **Rate limiting (Ограничение частоты)** | `time.Ticker` + канал | Позволяет выполнять действия с четко заданным интервалом (например, не чаще 5 запросов в секунду). |
| **Корректная остановка сервиса** | `signal.Notify` + `Shutdown()` | Паттерн **Graceful Shutdown**. Перехватывает системные сигналы (типа `SIGINT`, `SIGTERM`), перестает принимать новые запросы и дает старому коду доработать. |

---

## 💡 Золотые правила конкурентности в Go

1. **Не плодите горутины бесконтрольно.** Всегда знайте, как и когда горутина завершит свою работу. Утечка горутин — одна из самых частых проблем.
2. **Контекст идет первым.** Всегда передавайте `ctx context.Context` первым аргументом в функции, которые делают сетевые запросы, работают с БД или выполняют долгие вычисления.
3. **Проверяйте на Data Race.** Всегда запускайте тесты с флагом гонки: `go test -race ./...`.
